# AGENTS.md

Guidance for AI coding agents working in this repository.

## General Rules

- **No Automatic Commits**: NEVER run `git commit` or `git push` automatically without explicit user approval. Always wait for the user to review the changes and explicitly confirm before pushing code to the repository.


## Project Snapshot

- Project: Bulgarian school comparison site (НВО и ДЗИ)
- Hosting: GitHub Pages (`https://ivandavidov.github.io/nvo`)
- Type: static site - HTML generated by the Java tool from Mustache templates (plus a few hand-written pages), vanilla ES modules, JSON data. **No npm / no frontend build step.**
- Data source: `data.egov.bg` for the main site, plus per-region RUO raw files (PDF and/or XLSX) under `data/ruo-{region}/` for the `balove` pages
- Theme: light + dark only (follows the system until the visitor toggles it). There are no seasonal skins any more.

Public pages:
- `docs/index.html` - home (generated): search, one card per exam, balove, latest blog posts, data & tools. Legacy links with a query or hash (`/?i7=…`, `/#sofia`) still redirect to `./7/…`.
- `docs/{4,7,10,12}/` - grade pages (generated): comparison chart of selected schools + per-city rankings and averages
- `docs/{grade}/{city}/`, `docs/{grade}/{year}/` - city / national ranking pages (generated)
- `docs/{4,7,10,12}/embed.html` - embeddable charts for iframes (generated; see Embed section)
- `docs/school/{code}/` - per-school page (generated, grade-agnostic profile)
- `docs/7/balove/` - min/max admission scores: a hub (`index.html`) linking ~130 per-city pages (`docs/7/balove/{city}/`)
- `docs/stats/` - Обобщена статистика (31 analyses, hand-written page + `stats/logic.js`)
- `docs/blog/` - blog home (generated from `posts.json`) + hand-written posts `docs/blog/{slug}/`
- `docs/za-proekta/` - За проекта: methodology, data sources, contacts, support, useful links
- `docs/embed/` - embed documentation with a live code generator
- `docs/api/` - static JSON API (`api/` redirects to `api/v1/`, whose `index.html` is the interactive documentation)
- `docs/404.html` - GitHub Pages not-found page (sets `<base>` so it works at any depth)
- `docs/styleguide/` - internal, `noindex` page showing the design-system components (not linked, not in the sitemap)

The games, the gamebook and the console were removed in the redesign.

## Canonical Commands

### Full pipeline
```bash
./all.sh
```
Builds the Java tool, normalizes CSV/XLSX files, writes `docs/data/grade-{4,7,10,12}.json`, generates the API (`docs/api/v1/`), the city/year ranking pages, per-school pages, the balove pages, the grade pages + embeds, the blog home and the home page, the search index, syncs the shared layout into hand-written pages and writes `docs/sitemap.xml`.
The balove pages are generated before the grade data, because `data/grade-{grade}.json` exposes RUO availability through `si[city].r` based on the published `docs/{grade}/balove/{city}/` directories.

### Java tool - NvoDziDecomplexor (main jar)
```bash
cd java
./mvnw clean package
cd target
java -jar nvo-v2.jar normalize
java -cp nvo-v2.jar nvo.CodeCheck   # school-code check (fails on a code that is not 6-7 digits)
java -jar nvo-v2.jar 4      # → docs/data/grade-4.json (also 7, 10, 12)
```

### Java tool - JsonGenerator (separate entry point, uses `-cp` not `-jar`)
```bash
java -cp nvo-v2.jar nvo.api.JsonGenerator index
java -cp nvo-v2.jar nvo.api.JsonGenerator schools
java -cp nvo-v2.jar nvo.api.JsonGenerator school-pages
java -cp nvo-v2.jar nvo.api.JsonGenerator cities
java -cp nvo-v2.jar nvo.api.JsonGenerator 4   # also 7, 10, 12
```
- `index` generates `docs/api/v1/index.json` (API metadata) and `docs/api/v1/index.html` (interactive docs, on the shared layout)
- `schools` generates `docs/api/v1/schools.json`, `docs/api/v1/schools/{code}.json` (per-school cross-grade document) and `docs/api/v1/schools-index.json`. The school set is data-driven (codes that appear in the normalized data), not the full `School.schoolCodes` map.
- `school-pages` renders `docs/school/{code}/index.html` (template `school.mustache`) from the `schools/{code}.json` documents - must run after `schools`
  - Official school names live in the hand-maintained mapping `data/school-names.json` (same shape as `api/v1/schools.json`: `{"schools": {"<code>": {"monName", "officialName"}}}`). `monName` is the name exactly as in the MON register of institutions (`data/mon/ri-register.csv`: code, name, type, financing, status - a full snapshot of ri.mon.bg: every institution of every kind (schools, kindergartens, centres…), active and closed, sorted by code; CSV with every field quoted like `data/normalized/*.csv` - names contain commas and quotes, so it is read with OpenCSV; the API is behind Cloudflare, so it is fetched through a browser: POST `https://ri-api.mon.bg/data/get/public-register` with `{"isRIActive":1}` / `{"isRIActive":0}` (numeric `detailedSchoolType` / `financialSchoolType` / `transformType`), labels from POST `/data/get/detailedSchoolTypes`, `/data/get/financialSchoolTypesNoLimit`, `/data/get/public-transformTypes` (the valid label per code); every active variant is written as `действаща`, "преобразувана (закрито)" as "преобразувана (закрита)", names raw; the API also answers a page on localhost, so the snapshot can be posted from such a page to a local receiver), falling back to the exam CSVs only when a code is not in the register; `officialName` is the cleaned name: the name after the description in straight quotes (`Основно училище "Христо Ботев"`, `75. основно училище "Тодор Каблешков"`) - no quotes when nothing precedes the name (`Национална Априловска гимназия`) or there is no name (`Професионална гимназия по транспорт`); the quoted name is a proper name of its own, so its first word is capitalized even when it is a title (`"Св. Климент Охридски"`, `"Проф. д-р Асен Златаров"`, `"Цар Симеон Велики"` - as ИБЕ writes `Софийски университет "Св. Климент Охридски"`); titles in the middle stay lowercase (`"Св. св. Кирил и Методий"`, `"Свети апостол Йоан Богослов"`); the school type follows the register (the exam CSVs can be out of date); Bulgarian capitalization (personal names and towns capitalized, titles before a name lowercase - "проф. д-р Асен Златаров", "св. св. Кирил и Методий", "цар Симеон Велики"), "75. основно училище" (an Arabic ordinal takes a dot per ИБЕ, lowercase after it per the 2012 dictionary); a number written in words or in Roman numerals at the start becomes the same form ("Пето средно училище" / "V средно училище" -> "5. средно училище"), except established names that keep the word ("Първа английска езикова гимназия", "Първо частно средно училище ..."), abbreviations written out (ОУ → основно училище), commas in enumerations, double surnames and names with a hyphen ("Жолио-Кюри", always "Константин-Кирил Философ"), no town at the end (the page shows the city; quarters such as "- кв. Горно Езерово" and nicknames such as "- Майстора" stay). The build does no guessing: `OfficialNames` only reads the file. `SchoolsGenerator` copies both fields into `schools.json` and `schools/{code}.json` (null when missing) and prints the codes without an entry - add them by hand (one line per school) following the rules above, then check spelling. The short/full names from School.java stay untouched for tables and charts. Abbreviated middle names of a patron are written out with the form MON indicates for that school (the register, or the exam files for the same code); with no indication, "Г. С. Раковски" is "Георги Стойков Раковски", otherwise the indicated "Сава" / "Стойков". This applies to the official names and to the School.java full names; short names keep their abbreviations.
  - `registerStatus` (schools.json, schools/{code}.json) is the school's status in the MON register snapshot (`действаща`, `закрита`, `преобразувана (закрита)`, `отписана`, `заличена`, or null). A school that is not active gets a badge ("Закрито" / "Преобразувано" / "Отписано" / "Заличено") and a note in the hero of its page; its results and rankings stay.
  - The school page always shows `officialName` under the short H1 when the school has one; it also goes into the meta description and the JSON-LD `name` (the short name as `alternateName` when it differs), so searches by the full name match.
- `cities` generates `docs/api/v1/cities.json` and `docs/api/v1/cities/{slug}.json`
- `4`/`7`/`10`/`12` generates per-grade `data.json`, per-city `data.json`, per-school `.json` files, rankings under `docs/api/v1/rankings/`, and the city / year ranking pages (template `landing.mustache`)
- All per-grade API files share the envelope `{ grade, yearsRange, cities: { ... } }`
- Rankings: `rankings/{grade}/{year}.json` (per-year) and `rankings/median/{grade}/{year}.json` (3-year median window, from 2020 onwards, with `adjustedRank`)

### RUO / balove pipeline
The `balove` (min/max admission scores) pages now cover **~132 cities across 29 RUO regions**
(Sofia, Plovdiv, Varna, Burgas, Ruse, Stara Zagora, Pleven, Sliven, Dobrich, Shumen, Pernik,
Haskovo, Blagoevgrad, Yambol, Veliko Tarnovo, Pazardzhik, Vratsa, Gabrovo, Kurdzhali, Montana,
Vidin, Kiustendil, Turgovishte, Lovech, Razgrad, Silistra, Smolyan, Sofia Oblast, plus each
region's smaller towns). This covers all 29 RUO regions in Bulgaria.

```bash
java -cp nvo-v2.jar nvo.RuoNormalizer all          # Sofia only (XLSX -> normalized CSV)
java -cp nvo-v2.jar nvo.RuoDecomplexor <city>       # normalized CSV -> docs/js/ruo-<city>.js
java -cp nvo-v2.jar nvo.RuoPage <city>              # -> docs/7/balove/<city>/index.html
java -cp nvo-v2.jar nvo.RuoIndexPage                # -> docs/7/balove/index.html (hub of all cities)
```
- `RuoNormalizer` handles **only Sofia**: reads `data/ruo-sofia/*.xlsx` -> `data/normalized/ruo-sofia-{year}-normalized.csv`.
- **All other regions** were normalized by one-off Python scripts (kept in gitignored `tmp-ruo-{region}/` working dirs, not part of the build) that parse the mixed raw PDF/XLSX in `data/ruo-{region}/` directly into `data/normalized/ruo-{city}-{year}-normalized.csv`. Re-run a region's script only to regenerate its normalized CSVs. Parsing conventions used by those scripts:
  - **City = the settlement** (`Населено място` = `ГР.<city>`) matching a `Cities.java` city - **NOT the municipality** (a municipality also contains villages and other towns whose schools must not be filed under the city). Mirrors `NvoDziNormalizer.parseCity`.
  - **School codes**: taken from the raw file when embedded; otherwise recovered from MON **DZI-12** data (`data/mon/dzi-{year}.csv`) by settlement + school-name match. Clean school names come from MON too.
  - **Profile codes**: embedded when present; else reused from a year that had them (same school + profile name) or a stable synthetic code (the JS merges profiles by name across non-overlapping years anyway).
  - **Gender** breakdown is often absent → male/female columns written as `"0"`. Output format matches `ruo-sofia` exactly (12-col, `csv.QUOTE_ALL`, trimmed decimals).
  - **RUO Gabrovo** is a special case: the min/max score column positions vary unpredictably per file (not just by klasirane number - e.g. the "3rd stage" file has different column offsets in 2023 vs. 2024), so `tmp-ruo-gabrovo/` uses **one hardcoded script per raw file** (`file_{year}_{klasirane}.py`, verified row-by-row) instead of a single dynamic-column-detection parser, combined by `build.py`.
  - **RUO Kurdzhali** is similar (no 2023 data, no klasirane-4 file for 2024; same one-script-per-file approach in `tmp-ruo-kurdzhali/`, no gender breakdown anywhere). Data-quality note: `min_max_2_klasirane_2025.pdf` is a confirmed byte-identical duplicate of `min_max_3_klasirane_2025.pdf` (its own internal title says "Трети етап") - used as-is per user decision, so Kurdzhali's klasirane 2 and 3 scores are identical for 2025.
  - **RUO Montana** (`tmp-ruo-montana/`) never publishes klasirane-2 admission scores in any of its 3 years (only headcounts) - confirmed with the user; klasirane 2 is omitted entirely from the output, and the source's own "3 етап"/"4 етап" labels are trusted as-is (recorded as klasirane 3/4, not relabeled).
  - **RUO Vidin** (`tmp-ruo-vidin/`) and **RUO Kiustendil** (`tmp-ruo-kiustendil/`) have straightforward, internally consistent layouts (verified file-by-file) - Vidin only ever publishes 3 klasirania (no 4th stage at all), Kiustendil always uses the standard 15/18 min/max column offsets with full gender breakdown.
  - **RUO Turgovishte** (`tmp-ruo-targovishte/`; note the `Cities.java` slug is `turgovishte`, not `targovishte`) has 3 different formats across its 3 raw files (each confirmed with the user): the 2022-2023 file has no school-code column at all (codes recovered by settlement+name match against `data/mon/dzi-2022.csv`/`nvo-7-2022.csv`, cross-checked 100% against the embedded codes in the other two files); the 2024-2025 file has no "Общо" (total) column, only a Момичета/Момчета (girls/boys) split, so the total is derived (min = smaller nonzero gender value, max = larger gender value).
  - **RUO Lovech, Razgrad, Smolyan** (`tmp-ruo-lovech/`, `tmp-ruo-razgrad/`, `tmp-ruo-smolian/`) have simple, internally consistent layouts, no gender breakdown anywhere - each uses a single script with fixed column offsets, verified file-by-file (Smolyan's header wording varies a lot per file but the underlying column indices never move).
  - **Wrong school codes fixed by hand** in the normalized CSVs (12 rows): some raw files wrote the real code plus the profile's position (Хасково 2025 klasirane 3: 2601037/38/39 → 2601036 ПГМЕТ, 2601905/06 → 2601904 ПГТАТ; Любимец 2025 klasirane 3: 2606006/07 → 2606005; Смолян 2025: 2103322 → 2103321 ППМГ, 2100112 → 2100111 ПГТТ) or swapped digits (Ловеч 2023-2024: 1100311 → 1100331 ПГИТУ); the school name was set to the one the real code has in the same file. Re-running those regions' scripts brings them back - `RuoDecomplexor` then prints "code … is … in the MON register, not …" for such codes (a code that is not a site school and whose register name differs).
  - **RUO Silistra** (`tmp-ruo-silistra/`) splits city by the settlement column, NOT the "Община" column - some rows have an Община that does not match the school's own town (e.g. a Кайнарджа-municipality applicant attending a Дулово school), confirming the same rule used everywhere else in this project.
  - **RUO Sofia-Oblast** (`tmp-ruo-sofia-oblast/`) responded with two parallel file series per year - "RC7 ... класиране N" (the actual scores, used here) and "RC12 ... статус на записване" (enrollment headcounts only, no scores, ignored entirely). One of the twelve RC7 files (klasirane 3, 2025) arrived as a PDF instead of XLSX but has the identical column layout, parsed via `pdfplumber`.
- `RuoDecomplexor` (generic, takes a city slug) converts the normalized RUO CSVs into `docs/js/ruo-{city}.js` and the API document `docs/api/v1/balove/{city}.json` (same data; `coverage.{year}` = rankings with data + gender breakdown, gender `0` → `null`). Profile codes are canonicalized by stripping leading zeros (the raw files pad inconsistently - e.g. Sofia 2026 writes `03909` for `3909`), so a profile keeps one code across years and a renamed/repurposed profile keeps its history under the most recent year's name; profiles with identical names are additionally merged across years when data does not overlap. `findYears` strips the known `ruo-{city}-` prefix to read the year, so hyphenated slugs (`biala-ruse`, `stara-zagora`) work.
- `RuoPage` (generic) generates `docs/7/balove/{city}/index.html`.
- `RuoIndexPage` scans the published `docs/7/balove/*/` dirs and generates the hub `docs/7/balove/index.html`, grouping cities by `Cities.java` tier ("Областни градове" + "Други градове"). It makes every balove city discoverable even when a city has no `si[city]` entry (e.g. towns with no NVO-7 exam schools). It also writes `docs/api/v1/balove/index.json` (cities, years, counts) and `data.json` (all city documents) and deletes the JSON of cities without a published page.
- `all.sh` runs RuoNormalizer (Sofia), then loops every balove city through `RuoDecomplexor` + `RuoPage`, then `RuoIndexPage` last.

```text
                      special: nvo-7-2022-sofia.csv (Sofia-specific 2022 data)
                      note: nvo-10 data starts from 2021
  ruo-{region}/       raw RUO files for the 7th-grade min/max scores pages, one dir per
                      RUO region (ruo-sofia, ruo-plovdiv, ruo-varna, ruo-burgas, ruo-ruse,
                      ruo-stara-zagora, ruo-pleven, ruo-sliven, ruo-dobrich, ruo-shumen,
                      ruo-pernik, ruo-haskovo, ruo-blagoevgrad, ruo-iambol, ruo-veliko-turnovo,
                      ruo-pazardjik, ruo-vraca, ruo-gabrovo, ruo-kurdzhali, ruo-montana,
                      ruo-vidin, ruo-kiustendil, ruo-turgovishte, ruo-lovech, ruo-razgrad,
                      ruo-silistra, ruo-smolian, ruo-sofia-oblast)
                      naming: min_max_{1-4}_klasirane_{2023-2026}.{pdf|xlsx}
                      format varies per region/year (PDF and/or XLSX; some files missing;
                      2026: klasirane 1 imported for ALL 28 regions, klasirane 2 for 27
                      (all but Silistra), klasirane 3 for the regions that published it.
                      Most go through tmp-ruo-2026/build.py (it combines klasirania 1-4 into
                      one CSV per city, skipping missing files, and takes a region filter);
                      Haskovo/Pernik use their own scripts and Vratsa uses
                      tmp-ruo-vraca/build_2026.py (its files drop the settlement + school-code
                      columns). 2026 profile codes are 5-digit everywhere, zero-padded in some
                      regions - RuoDecomplexor canonicalizes them.
                      Gabrovo 2026 klasirane 1 arrived as an image-only scanned PDF; the user
                      hand-typed a machine-readable XLSX from it (standard 21-col layout).
                      Montana 2026 has one source row with min>max dropped as impossible.
                      PROBLEM: ruo-vidin/min_max_3_klasirane_2026.xlsx is titled "КЛАСАЦИЯ ПО
                      УЧИЛИЩЕ" and has NO Паралелка columns - it is a per-SCHOOL aggregate
                      (school, Класирани, min/max), so it cannot be imported into the
                      per-profile model; awaiting a per-paralelka file from the user)
  normalized/         processed CSV files (generated by NvoDziNormalizer / RuoNormalizer / one-off scripts)
                      naming: {grade}-{year}-normalized.csv
                      RUO naming: ruo-{city}-{year}-normalized.csv (per CITY, not per region)
  *.xlsx              historical Excel archives (not used in pipeline)
```

### Data flow
```text
data/mon/*.csv -> data/normalized/*.csv -> java (NvoDziDecomplexor) -> docs/data/grade-{grade}.json
                                        -> java (nvo.api.*)          -> docs/api/v1/ (JSON API + docs page)
                                                                       + city/year pages + docs/school/{code}/
docs/data/grade-*.json + docs/blog/posts.json -> java (nvo.site.*) -> grade pages, embeds, home, blog home
api/v1/schools-index.json + cities.json       -> SearchIndexGenerator -> docs/data/search-index.json

data/ruo-{region}/*.{pdf,xlsx} -> data/normalized/ruo-{city}-*.csv  (Sofia via RuoNormalizer;
                                                                    other regions via one-off scripts)
data/normalized/ruo-{city}-*.csv -> java (RuoDecomplexor) -> docs/js/ruo-{city}.js
                                  -> java (RuoPage)        -> docs/7/balove/{city}/index.html
                                  -> java (RuoIndexPage)   -> docs/7/balove/index.html (hub)
```
`NvoDziDecomplexor` detects published `docs/{grade}/balove/{city}/` directories and sets `si[city].r` in `grade-{grade}.json`, which lets the grade pages show a `Балове` button for supported cities.

`SchoolsGenerator` aggregates the normalized CSVs across all four grades into per-school documents (`docs/api/v1/schools/{code}.json`) plus `schools-index.json`; `SchoolPageGenerator` renders `docs/school/{code}/` from those documents and inlines the same JSON for `js/pages/school.js`.

### Shared layout (one source for head, header and footer)
- Templates live in `java/src/main/resources/templates/` (JMustache): `partials/head|header|footer.mustache` and the page templates `grade`, `embed`, `landing`, `school`, `balove-city`, `balove-hub`, `blog-index`, `home`.
- `nvo.site.SiteLayout` renders the partials for a page (`new SiteLayout.Page(root).active(...)`); generators pass them into their template. `{{#icon}}name{{/icon}}` inlines an SVG from `nvo.site.Icons`.
- Hand-written pages mark the blocks and `LayoutSync` fills them (idempotent, run by `all.sh`):
  ```html
  <!-- nv:head favicon="favicon-7.png" css="blog.css" --> … <!-- /nv:head -->
  ```

### Design system and theme
- `docs/css/site.css` is organised in `@layer reset, tokens, base, legacy, layout, components, pages, utilities`. ### UI conventions (keep layouts calm and aligned)
- One row, one visual language: controls that sit in the same row share one component and height (e.g. the grade hero row = navigation chips, all 32px high). Never stack a control under another one where it breaks the alignment of the block. Every dropdown trigger shows a caret.
- Phones (≤ 640px): a row of buttons that does not fit becomes a grid of two equal columns (40px high) - no ragged rows, no lone button on its own row; with an odd count the first (most important) button spans the full width. Labels get shorter (`chip__short`, `tabs__long`) instead of wrapping or scrolling sideways; tab bars split the width equally and never scroll.
- Actions vs navigation: data actions (export) are one menu, set apart from navigation. The "Изтегли данните ▾" button looks the same everywhere (`btn btn--sm`, like above the city tables) and follows the links of its row after a vertical divider (grade hero, city panel); on phones it is a cell of the two-column grid - rule 10.
- Tab views: the control that changes what the tabs show sits at the right of the tab bar - on the grade city panel that is "Покажи само" (the school types, one filter for both tabs); when the tabs and the chips do not fit in one row (tablet, phone - the limit depends on the number of types, `data-types` + container queries on `.city-panel__bar`) the chips are a row under the tabs. Content starts right under the tab bar. Do not add rows to the panel head - it is one row: the city name | the count, then links/export.
- School types: state (Д), municipal (О), private (Ч), religious (ДУ) - one colour each (`--type-s|m|p|r` + `-soft` tokens, `.type-badge--{key}`), the same letter and colour in the chips, the "Тип / №" column, the averages headers on phones, the school page badge and the stats chart. "Покажи само" (`.type-filter` with `.chip.type-chip[aria-pressed]`; in the tab bar of the grade city panel, a row in the table head on the city/year pages): nothing selected = all types; a click adds or removes a type; only types present (and only with at least two). On phones the chips are an equal-column grid (2 types: 2 columns, 3: 3 columns, 4: 2×2), each chip two lines (name, then letter + count).
- Data tables: one header row when every column can carry its own short label (subject + qualifier, e.g. "БЕЛ 26" in the ranking - two-digit year, the full year for screen readers and in the tooltip - with the qualifier in `.th-qual`); a group row (`colspan`, ungrouped columns `rowspan`) only where it keeps a narrow table on a phone without sideways scrolling (none at the moment). No empty header cells and no legends in the header; header cells align like their data (the name column left, the others centred); vertical dividers only between column groups. The key value sits right after the name, so on phones the sticky № + name + key value are visible without sideways scrolling and the next column peeks in. The ranking table fits at 1280px for every grade (also "ДЗИ-2 26").
- Tables on phones and touch devices (`(max-width: 767px), (hover: none) and (pointer: coarse)` - the same query in site.css and `TOUCH_TABLES` in `ui/sticky-head.js`): `.table-wrap` has no vertical scroll of its own (`max-height: none`), so a vertical swipe over a table scrolls the page and only sideways swipes scroll the columns; the header row stays visible as a floating copy under the sticky top bars (`.site-header`, `.school-nav`, `.stats-toc`), synced sideways and pushed up at the table's end. The copy is `aria-hidden`; a tap on it clicks the same control in the real header and scrolls back to the table's top. The copy lives outside the table, so it gets the computed `display` and `text-align` of the real header cells inline (rules by ancestor / container queries do not reach it). Desktop keeps the inner scroll and the sticky `thead`.
- Balove "Топ паралелки" table: below 1024px (`OVERVIEW_COMPACT` in `pages/balove.js`, re-rendered on change) "Училище" and "Паралелка" are one sticky column with two lines (school, then the profile) and two stacked sort buttons in the header (`.is-sorted`/`.is-asc` mark the active one); its width follows the table (container query): just enough for № + the column + the latest year on narrow screens (at least 9rem), all the free space once every column fits. Names wrap (never clipped); year headers are "Мин. 26".
- Every UI change is checked with screenshots at 320 / 360 / 390 / 768 / 1280 / 1440 px in both themes (and keyboard + axe) before it is shown - and looked at critically as a whole screen, not only measured for overflow. Floating helpers (the "N училища в графиката · Виж" bar) are checked on every width, not only on phones.

## Generated Data Contract

`docs/data/grade-{grade}.json` (one per grade; same shape the old `schools-{grade}.js` had):
```javascript
{
  grade: 7, source: "https://data.egov.bg/…", firstYear: 2018,
  si: { "София": { n: [start, end], p: [start, end] | null, l: "short label", h: "slug", o: 1, i: 0, r: true } },
  s: [ null, { l: "short label", n: "full name", b: [...], m: [...], bu: [...], mu: [...], w: "website" | null, c: "code" }, … ]
}
```
- `s` is indexed from 1 (the index is what the legacy `?i{grade}=` parameter refers to); `b`/`m` = BEL/MAT (DZI-2) scores by year from 2018, `bu`/`mu` = participants; `null` = no data.
- `s[i].t` = school type (`SchoolType.key`): `s` state, `m` municipal, `p` private, `r` religious.
- `si`: `n`/`p` = non-private / private index ranges (unchanged order, so the legacy `?i{g}=` indices stay stable), `l` label, `h` slug, `o` tier (1-3), `i` order, `r` = has a balove page for this grade.

`docs/data/search-index.json`: `{ schools: [[code, shortName, fullName, citySlug, isPrivate(0|1), [grades], officialName, type]…], cities: [[slug, name, orderPosition, [grades with a page], hasBalove(0|1)]…] }` (`type` = `s|m|p|r`).

School types come from the MON register snapshot `data/mon/ri-register.csv` (column `financing`: Държавно / Общинско / Частно / Духовно) through `nvo.SchoolType.of(code)` (`nvo.MonRegister` reads the file once). The register is the only source; the private flag in `School.java` is only a fallback for a code missing from the register, and the build prints such codes ("SchoolType: … refresh the register snapshot") - refresh the snapshot when new schools appear. The JS twin is `docs/js/core/school-types.js` (key, letter, labels, API value). The public API adds `financing` (`state|municipal|private|religious`) next to every `isPrivate` (which stays), `balove/{city}.json` has `financing: null` for RUO codes missing from the register; a RUO code that is not a site school (not in School.java) gets its type only when its register name matches the RUO name (`RuoDecomplexor.sameSchool`: the significant words of the shorter name, abbreviations such as ПГ/СУ written out, are all in the other) - some RUO codes are synthetic or wrong and belong to another institution in the register, and the build prints them ("RuoDecomplexor: code … is … in the MON register"); financing "По силата на международен договор" (3 international schools) has no SchoolType, and `schools/{code}.json` → `grades.{g}` has `nationalTypeRank/nationalTypeTotal` and `cityTypeRank/cityTypeTotal` (shown on the school page as "Сред частните" etc., the city one only when the city has other types too).

In `schools/{code}.json` (per-school cross-grade API document, also inlined in the school page):
```javascript
{
  code, fullName, shortName, isPrivate, financing, website,
  city: { slug, name },
  yearsRange: [2018, /* … */],
  grades: {
    "7": {
      yearsRange, belScore: [/* … */], matScore: [/* … */], belStudents: [/* … */], matStudents: [/* … */],
      latestYear, nationalRank, nationalTotal, cityRank, cityTotal,
      nationalTypeRank, nationalTypeTotal, cityTypeRank, cityTypeTotal,
      medianRank, medianAdjustedRank, medianTotal, medianEndYear,
      nationalRanks, nationalTotals, cityRanks, cityTotals   // per year, aligned with this grade's yearsRange; null = no rank
    }
  }
}
```

In `schools-index.json` (public API): `{ schools: [ { code, shortName, fullName, isPrivate, financing, city, cityOrder, grades: [4, 7] } ] }`.

In `ruo-{city}.js`:
```javascript
let ruoYears = [2023, 2024, 2025];
let ruoSchools = {
  "schoolCode": {
    n: "short school label", f: "full school name", c: false,
    p: { "profileCode": { n: "profile name", d: [ [null, [/* 6 scores */], null, null], /* next year */ ] } }
  }
};
```
- `d` = per-year array aligned with `ruoYears`; each year has 4 ranking slots (`0` = first ranking); each score entry is `[min_total, min_male, min_female, max_total, max_male, max_female]`; `null` = already filled in a previous ranking. The balove page loads it as a classic `defer` script before `js/pages/balove.js`, which reads the globals.

## Important Rules

1. Do not manually edit generated files: `docs/index.html`, `docs/{4,7,10,12}/index.html` and `embed.html`, `docs/{grade}/{city|year}/`, `docs/school/**`, `docs/7/balove/**/index.html`, `docs/blog/index.html`, `docs/data/*.json`, `docs/js/ruo-*.js`, `docs/js/ui/icons.js`, `docs/api/v1/` (all contents), `docs/sitemap.xml`. Change the template / generator and run `./all.sh`.
2. Inside hand-written pages never edit between the `<!-- nv:* -->` markers - change the partial templates and run `LayoutSync`.
3. Keep relative paths correct for nested pages (`../` vs `../../`); generators compute them from depth (`SiteLayout.rootFor`).
4. Highcharts and jsPDF are vendored; avoid unnecessary upgrades unless requested.
5. Keep the public URL contract: `?i{g}=`, `?s=`, `?school=`, `?year=`, `#city` on grade pages; `?grade=` on stats; `?school&profile&gender` on balove pages; embed parameters; `/?…` → `/7/…`. The public JSON API must stay backward compatible.
6. New UI goes into `site.css` layers using the tokens; avoid inline colours.
7. School codes: `NvoDziNormalizer.canonicalCode()` is the only place that cleans codes from the MON files. The NVO 7 2018 file writes some codes as `800-08` (a decimal that lost its trailing zeros) - they are padded back (`800080`). `CodeCheck` (in `all.sh`) stops the build on any code that is not 6-7 digits, so a new format shows up before it creates phantom school pages. Old phantom profile URLs are kept as redirects (`SchoolPageGenerator.LEGACY_REDIRECTS`, excluded from the sitemap).
8. Same school name in the same city under different codes (MON changed the code) - the profiles get the year range in the title/description and link to each other. Once the code change is confirmed in the MON register, add it to `NvoDziNormalizer.CODE_ALIASES` (old → current code) and the old profile URL to `SchoolPageGenerator.LEGACY_REDIRECTS`; the history is then merged under the current code (done for ОУ "Иван Вазов", Кюстендил: 1000340 → 1000005).
9. Displayed years: charts, tables and PDF reports show only the window `max(DISPLAY_FROM, latest - 7)…latest` (historical `?year=Y`: the last 3 years, selectable from `DISPLAY_FROM + 2`). Earlier years stay only in the exports - CSV (`model.exportData`), JSON API, Kaggle, `data/grade-{g}.json` - as raw MON values (NVO 7 2018 is on a 65-point scale; there is no rescaling anywhere). Year pages start at `DISPLAY_FROM`; older year URLs are redirect stubs (`GeneratorUtils.writeRedirectPage`, excluded from the sitemap). The window slides by itself when a new year is added.
10. Exports are uniform: every grade page and balove page has one "Изтегли ▾" menu (`<details class="menu-button" data-popover>`, markup from `nvo.site.ExportMenu` / `js/ui/export-menu.js`, behaviour in `js/ui/popover.js`) for one city and one for all cities - CSV and JSON are data (all years, raw; JSON is the static API file), PDF is the report of what the site shows (displayed window). Balove CSV/PDF are built in the browser from `api/v1/balove/*.json` (`js/core/balove-export.js`); the grade all-cities PDF is `allRankingsPdf()` in `js/core/pdf.js`. Do not add separate export buttons next to navigation buttons.

### School brochure PDF
`js/core/brochure.js` (vector jsPDF + AutoTable, no Highcharts, generated in the browser - pre-generated PDFs would put ~1400 files into git on every data update). The school page button ("Изтегли PDF", `schoolBrochurePdf(data)` with the inlined document) and the "Доклад" button of the grade ranking tables (`schoolBrochureByCode(code)`, loads `api/v1/schools/{code}.json`) give the same brochure:
- cover: name, official name (only when it differs), type / city / code / status / website chips, "Място в страната" per exam (rank, "пред X% от училищата", БЕЛ/МАТ with the difference from the national average, city and 3-year rank), "Акценти" (only strengths, by fixed rules in `highlights()`: the strongest fact of every exam that has one, a second fact of an exam only while there are at most 4 exam facts, listed НВО 4 … ДЗИ 12, then the balove line after a blank line, in the first of its wordings that fits on one line; the section is left out when there are none). The PDF calls itself "профил", never "брошура", contents with page links and a QR code to the school page
- one page per exam with results in the displayed window (rule 9): KPI tiles, a summary strip (3-year average, best rank, best scores), БЕЛ/МАТ charts with the national average and the average of the same type in the city (only when the city has other schools of that type), national rank by year (inverted axis), the year table (Δ from the national average, national and city rank)
- "Прием след 7 клас" when `api/v1/balove/index.json` lists the city and the school has profiles: min-max bars of the 1st klasirane in the latest year, then min of the 1st klasirane by year + the last klasirane (active profiles first)
- "Близки по успех в {град}": per exam the schools around this one in the city ranking of its latest year (all of them in small cities)
- "Как да четем данните" (definitions, years, sources, a note that exams show only part of a school's work)
- Data: ranks by year come from the API arrays (`nationalRanks`…, the same numbers as the KPIs); the national average and the same-type city average from `data/grade-{g}.json` via `model.js` (as on the grade pages); schools missing from `grade-{g}.json` (closed) find their city by slug and are added to the city list from the API. ## Kaggle Dataset

The `kaggle/` directory contains everything needed to publish and maintain the Kaggle dataset.

### Structure
```text
kaggle/
  dataset-metadata.json   Kaggle dataset metadata (title, subtitle, tags, resources)
  kernel-metadata.json    Kaggle notebook metadata (for `kaggle kernels push`)
  README.md               dataset description (shown on Kaggle dataset page)
  notebook.ipynb           exploratory analysis notebook (published on Kaggle)
  prepare.py               converts JSON API → 4 CSV files in data/
  generate_cover.py        generates cover.png for the Kaggle dataset page
  cover.png                generated cover image (1128×568)
  data/                    generated CSV files (gitignored)
    scores.csv             29,301 rows - scores per school/grade/year
    rankings.csv           52,434 rows - annual + 3-year median rankings
    schools.csv            1,417 rows - school directory (data-driven: schools that appear in the data)
    cities.csv             145 rows - city directory
```

### Workflow
The CSV files are generated from the JSON API (`docs/api/v1/`), so the full pipeline must run first:
```bash
# 1. Run the full data pipeline (builds Java tool, generates API)
./all.sh

# 2. Generate Kaggle CSV files from the API
cd kaggle
python3 prepare.py

# 3. (Optional) Regenerate cover image
python3 generate_cover.py
```

After generating the CSVs, upload to Kaggle via the Kaggle web interface or CLI.

The notebook (`notebook.ipynb`) is stored without outputs - Kaggle runs it server-side on publish.

To publish the notebook from the repo (instead of editing on kaggle.com), use the Kaggle CLI with `kernel-metadata.json` (requires an API token in `~/.kaggle/kaggle.json`, created from Kaggle → Settings → API):
```bash
cd kaggle
kaggle kernels push -p .
kaggle kernels status johnddavidson/initial-exploratory-analysis-2018-2026  # check the server-side run
```
`dataset_sources` in `kernel-metadata.json` is unpinned, so each push runs against the latest dataset version.
